# Replace Selection: confirm the paste by reading the focused field

Status: accepted — 2026-11-06

## Context

Replace Selection pastes with a synthesized ⌘V and showed "Replaced" whenever
the translation came back. Nothing checked that the other app took the paste,
so a read-only field, a page that cancels `paste`, or a field that lost focus
during the run all reported success while the text stayed the same. This was
reported on web forms in Chromium browsers.

## Decision

- Before ⌘V, read the frontmost app's focused element's `AXValue`. Check it
  only when it contains the selection that `copySelection()` returned, so we
  know it is the field being edited. After ⌘V, poll it for up to 1 s. If it
  never changes, fail with `pasteNotApplied` and leave the translation on the
  clipboard so the user can paste it by hand.
- Any other case counts as pasted, as before: no readable element, an element
  that does not show the selection (a web area, a rich editor's proxy element),
  or a translation identical to the selection.
- Query the focused element once at copy time too. Safari and Chromium answer
  the first query empty while they build their accessibility tree.
- Read the app element's `AXRole` before its focused element. In Chromium
  (main, 2026-11) that read is what turns on web-content accessibility
  (`kAXModeBasic`, `chrome_browser_application_mac.mm`). We do not set
  `AXEnhancedUserInterface`: it turns on full screen-reader mode after a 2 s
  delay, and it is known to break window animations and window managers.
- Note where the selection came from right after the copy: the frontmost
  app, its focused element (kept only when two queries return the same
  element), and the selected range. Before ⌘V, require that app in front,
  that element focused and, when it could be read at copy time, the same
  selected text. Otherwise activate the app, focus the element, set the
  range, and check again once. If it is still not in place, send no ⌘V,
  fail with `targetLost` and leave the translation on the clipboard. The
  "did it change" check then reads that same element.

## Consequences

- Measured in Safari on a test page: a normal field changed after 0.09 s. A
  read-only field, a field that cancels `paste`, and a field that reads the
  clipboard and then cancels all stayed the same and are now reported.
- Selecting non-editable page text still reports "Replaced": the focused
  element there is the page, which does not contain the selection.
- An app whose `AXValue` lags more than 1 s behind a real paste would get a
  false failure. The failure leaves the translation on the clipboard, so
  nothing is lost.
- Measured in Safari through `SelectionCapture` itself: after switching to
  Finder during the wait, the paste went back into the copied field. When
  the tab moved to another page with a different field focused and selected,
  it failed with `targetLost` and that field was left untouched.
- Without an Accessibility element only the app is checked; switching to
  another app still stops the paste.
- The Chromium behaviour comes from reading the source and has not yet been
  run against a real Chrome. Whether macOS lets TransFlex (an agent app)
  activate the other app has only been run from a command-line process; if
  it does not, restoring fails safely into `targetLost`.

## Rejected

- Lazy pasteboard data (`NSPasteboardItemDataProvider`), counting a read after
  ⌘V as "pasted". Chromium only reads the text when it really inserts it, so in
  theory this works. But on the owner's Mac a background reader (likely
  Alfred's clipboard history) read the data within 0.1–0.9 s in 6 of 6 runs
  even with no ⌘V sent. It also ignored the `org.nspasteboard.TransientType`,
  `ConcealedType` and `AutoGeneratedType` markers. The signal is meaningless
  wherever a clipboard manager runs.
- Setting `kAXSelectedTextAttribute` instead of pasting: React-style inputs do
  not see the change, and many apps do not support it (see `SelectionCapture`).
